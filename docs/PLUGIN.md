# Native plugin (VST3 / AU / CLAP / LV2 / Standalone)

`plugin/` is the native port: a C++20 audio engine (`plugin/core`, no JUCE) inside a
JUCE 9 plugin whose editor is **the web app itself**, bundled into the plugin binary and
shown in the operating system's web view (WebView2 on Windows, WKWebView on macOS,
WebKitGTK on Linux): no external browser, no network. Generation (Seed / Mutate /
Breed, formulas), the Timeline, wavetable management, voices, sequences and MIDI settings
are the same TypeScript code as the browser build; only the audio runs natively.

## Build

Requirements: CMake ≥ 3.22, a C++20 compiler (Xcode 15+, VS 2022, GCC 11+ / Clang 14+),
Node 20+ (the build runs `npm ci` if needed and `npm run build`, then zips `dist/` into
the binary). On Linux, JUCE's dependencies plus `libwebkit2gtk-4.1-dev` (see
`.github/workflows/plugin.yml` for the apt list); building the LV2 needs a display (the
manifest step loads the plugin): use `xvfb-run` on a headless box. On Windows CMake
downloads the WebView2 SDK (NuGet) and links its loader statically; the WebView2 runtime
ships with Windows 10/11.

```sh
cmake -S plugin -B build -DCMAKE_BUILD_TYPE=Release   # fetches JUCE 9.0.4 + clap-juce-extensions
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure  # core tests + VST3 host test
```

Artefacts land in `build/mkwavez_artefacts/Release/{VST3,CLAP,AU,LV2,Standalone}`
(`-DMKWAVEZ_COPY_PLUGIN=ON` also installs them into the user plugin folders). Options:
`MKWAVEZ_WEBVIEW` (ON; OFF = the minimal native editor, no web view dependency),
`MKWAVEZ_BUILD_WEB` (ON; OFF = embed an existing `MKWAVEZ_WEB_DIST`), `MKWAVEZ_CLAP` (ON),
`MKWAVEZ_HOST_TEST` (ON), `MKWAVEZ_PLUGIN=OFF` builds only the core and its tests (no
JUCE download; seconds):

```sh
cmake -S plugin/core -B build-core && cmake --build build-core && ctest --test-dir build-core
```

Runtime switches: `MKWAVEZ_WEB_DEV_URL=http://localhost:5173` loads the Vite dev server
instead of the embedded build (edit the UI without rebuilding the plugin);
`MKWAVEZ_NATIVE_EDITOR=1` uses the minimal native editor; `MKWAVEZ_WEB_DEBUG=1` prints the
page's errors / warnings to stderr (`=2` also traces the protocol).

Offline / local checkouts: `-DFETCHCONTENT_SOURCE_DIR_JUCE=/path/to/JUCE`,
`-DFETCHCONTENT_SOURCE_DIR_CLAP_JUCE_EXTENSIONS=/path/to/clap-juce-extensions`.
Editor screenshot: `cmake --build build --target mkwavez_snapshot` then run
`mkwavez_snapshot out.png` (under `xvfb-run` on a headless Linux box).

CI (`.github/workflows/plugin.yml`) builds and tests on Linux, macOS (universal) and
Windows on every push and pull request that touches `plugin/`, `src/` (the web app the
editor embeds), the build setup or the golden / parity tests, and on demand (Actions →
Plugin → Run workflow, any branch); it uploads the plugins as workflow artefacts. A
newer push to the same branch cancels a run in progress. The golden and parity tests
also run on every push to `main` with `npm test` in the Pages workflow. Builds are
unsigned (macOS: notarisation is a later step).

**Which build is running:** the Session menu's last line (and the tooltip on the title)
names it — the tag, or `v<version> · <commit> · <date>` (`· dirty` for a build with local
edits) — and ends in `· plugin` when the page runs inside the plugin. The plugin embeds the
page built with it, so this names the plugin build. If a host still shows an older build,
look for other copies (VST3: `~/Library/Audio/Plug-Ins/VST3` and `/Library/Audio/Plug-Ins/VST3`;
AU: `…/Components`; Windows: `C:\Program Files\Common Files\VST3`) and have the host
rescan; on macOS a quarantined download may need `xattr -dr com.apple.quarantine` on the
bundle before a host loads it.

**Licensing:** JUCE 9 is AGPLv3 or commercial. Distributing binaries means either
releasing mkwavez under the AGPL or holding a JUCE licence. The core (`plugin/core`)
doesn't depend on JUCE. The VST3 SDK is MIT-licensed; CLAP is MIT.

## Layout

```

    include/mkwavez/        constants, prng, dsp (fft, shape, basic waves, mip sets),
                            playback (PackedWavetable, resolveMix), voice + sequence,
                            envelope (Adsr, NoteStack), midi (parse, router incl. mod
                            wheel / aftertouch, CC map with the synth targets),
                            synth + modulation (Synth voice params, LFOs, mod matrix),
                            svf (ZDF filter, drive, limiter), wtosc (wavetable
                            oscillator), synth_voice (the Synth voice path), table_map,
                            spsc_queue, engine (SynthEngine: Simple + Synth voices,
                            stereo, CPU guard)
    tests/                  golden.cpp (vs the TS core), engine / misc tests,
                            golden/core.golden.txt (generated by tests/golden.test.ts)
  source/                   the JUCE plugin
    EngineHost              Document (engine-facing project state) + command queue +
                            memory ownership / retirement
    PluginProcessor         processBlock: commands, parameter overlay, host transport,
                            sample-accurate MIDI; state save / load
    Parameters              APVTS layout (4 voice slots × (13 voice + 16 Synth params) + globals)
    State                   Document ⇄ ValueTree (binary table data)
    SynthJson               SynthParams ⇄ JSON (the TS field names; page voices + state)
    WebEditor               the editor: WebBrowserComponent + the zipped web build
                            (resource provider), 30 Hz poll
    WebLink                 the native end of the page protocol (decode edits, init /
                            tables, status, transport, automation, controller moves)
    PluginEditor, WavetableView, Theme   minimal native editor (fallback)
  tests/HostTest.cpp        loads the built VST3 like a DAW and checks it
  tests/WebTest.cpp         end to end with the real web view (Linux, xvfb)
  tests/Snapshot.cpp        renders the native editor to a PNG
src/audio/port.ts           EnginePort: WorkletPort (browser) | NativePort (plugin)
src/audio/nativePort.ts     the page end: JUCE's window.__JUCE__.backend, one event id
src/plugin/host.ts          plugin mode: PluginSessionStore (the session backend), boot,
                            host changes → model
```

## How the plugin works

```
 web view (the web app)                              native (C++)
 AppModel ── AudioBridge ── NativePort ──event "mkwavez"──► WebLink ── EngineHost ──SPSC──► SynthEngine
   ▲   (same reconcile code as the        (JSON; tables          │   (document, mip sets,      (audio thread)
   │    browser, raw tables)               as base64)            │    memory retirement)
   │                                                             ├─► parameters (V1–V4, Play, BPM)
   └── PluginHost ◄── init / records / status / transport / ─────┘   session (saved with the state)
                      voice/params / midi/cc
```

- **Same model, same reconcile.** The page's `AudioBridge` talks to an `EnginePort`; in
  the browser that is the AudioWorklet, in the plugin `NativePort`, which sends the same
  batched protocol (`audio/protocol.ts`) to the native side as JSON, with raw tables
  (`tables/addData`, base64 float32) because the native side builds the mip sets. A batch
  becomes one atomic command batch on the audio thread, as in the worklet.
- **State lives natively.** `EngineHost`'s document (tables with samples, wavetables,
  voices, sequences) is what plays; it keeps playing with the editor closed and is saved
  with the plugin state, together with the page's **session** (the web app's own format,
  `src/core/session.ts`: meta JSON + one record per waveform) and the plugin-only page
  settings (MIDI routing). The page uses its regular restore (`app/restore.ts`) and
  autosave (`app/autosave.ts`) with `PluginSessionStore` as the backend: opening the
  editor, the page says `hello`, gets `init` (session meta, current parameter values,
  transport, the ids the engine holds) and the waveform records in chunks, restores (or
  starts the default session), reconciles with what the engine holds (a restored session
  re-sends no tables), and autosave writes changes back (250 ms debounce, since the editor
  can close at any time). A state load by the host while the editor is open reloads the
  page. Session → Export / Import (.mkwz) is shared with the browser build.
- **Preview tables.** Generate's unadded waveforms (ids from `PREVIEW_ID_BASE` = 2^30)
  reach the engine only while a voice plays the Preview / Preview batch wavetable, as in
  the browser, and are left out of the saved state (`state::toValueTree`): after a restore
  those slots stay silent until the editor shows a preview again.
- **Host integration.** Voice slots V1–V4 (voice ids 1–4) expose 29 automatable
  parameters each (13 voice fields, 16 Synth: the macros first); the page's voice edits set them, and automation flows back to the
  page's model (polled at 30 Hz, so nothing touches the web view from the audio thread).
  The init message carries the current values, so automation made while the editor was
  closed wins over the saved project. Play / BPM work the same way.
- **Driven by the host's MIDI.** A fresh instance starts with one Synth voice (V1) that the
  host's MIDI plays. Generate, Timeline and Voice start open (Wavetables and Sequence
  collapsed), and the editor opens at 1400 × 880, so the Voice panel shows the Synth's full
  view: every control, with the values under the knobs once the window is about 1360–1500
  wide (by the web view's fonts; below that they show on hover). A much smaller window
  switches it to the compact pages. The internal sequencer doesn't follow the host's transport unless
  **Sequencer follows host** is on (off by default): it runs from the page's Play. **Host
  sync** (on by default) makes the tempo follow the host (tempo-synced LFOs, and the
  sequencer when it runs); the page shows the effective transport. Projects saved before
  *Sequencer follows host* existed keep their old behaviour (it follows Host sync).
  Session → New in the plugin starts the same one-voice session. MIDI comes from the host: the native router applies it at the sample offset;
  the page's MIDI panel shows "Host MIDI", and its settings (on / off, Omni, MPE, CC map; saved
  in the project) drive the native router; controller messages come back to the page for
  learn, the LED and the sliders.

| Web app (browser) | Plugin |
| --- | --- |
| `src/core/*` DSP, playback, engine, MIDI | `plugin/core` (1:1 C++ ports, golden-tested) |
| AudioWorklet + `audio/protocol.ts` | `WebLink` → `EngineHost` → lock-free SPSC → `SynthEngine` |
| GC keeps a removed table alive while a voice fades it out | the engine retires pointers (`popRetired`) only once no voice plays them; `EngineHost::housekeeping` frees them |
| Web MIDI (render-quantum jitter) | host MIDI, applied at its sample offset |
| BPM / Play | host tempo (Host sync) or the BPM parameter; the sequencer runs from Play, or with the host's transport when *Sequencer follows host* is on (off by default: MIDI plays the voices) |
| start session: three Simple voices, each with a sequence | one Synth voice (full view, Generate and Timeline open) played by the host's MIDI, its sequence kept for Play |
| localStorage MIDI settings | saved with the plugin state |
| IndexedDB autosave (one tab owns it) | the same autosave into the plugin state (one page per instance) |
| `confirm()` / `prompt()` | an in-page dialog (`ui/dialogs.ts`): macOS WKWebView under JUCE answers them with false / null |
| downloads / `<input type=file>` (Session, preset and shape-chain export / import) | native save / open dialogs (`FileHost` in `ui/session.ts`, `WebEditor::saveFile` / `openFile`) |

Audio-thread rules carried over: no allocation, no locks, no FFT in `processBlock`; the
engine uses fixed pools (16 voices, 32 sequences, 64 wavetables, a 16384-slot open-
addressing table map) instead of Maps.

## Verification

- **Golden fixture** — `tests/golden.test.ts` runs the TS core on fixed inputs (PRNG,
  shape, basic waves, mip sets, mip levels, modulated position, velocity / note
  frequency, ADSR, 400 random `resolveMix` cases over 1D / 2D / Rows with empty slots,
  the synth helpers (SVF in every mode, drive, limiter, LFO shapes), and ten engine
  scenarios with timed commands, rendered in stereo: sequencer + Blend/Step switches, MIDI
  on a sparse 2D wavetable, step lengths, Rows + late / removed tables, and six Synth
  voice scenarios — most of the path at once (osc B on 2D, sub, pink noise, ring, FM,
  LP24 with drive / key tracking / envelopes, pitch envelope, glide, unison spread +
  width, saturation, three LFOs incl. tempo-synced S&H, a full mod matrix, bend / mod
  wheel / aftertouch), live edits (filter modes, hard sync, unison 4 → 1 → 2, ADSR mod
  envelope, retriggered LFOs, legato glide, Simple ↔ Synth switches on a held note),
  the unison CPU guard, and the stereo path (oscillator pans, stereo phase, stereo position
  on Blend and Step wavetables, noise width, filter spread, stereo LFOs on per-channel
  destinations, then back to mono), and polyphony (chord, stealing, same-key reuse, poly
  glide, a polyphonic sequencer voice with overlapping tails, poly → 1, a Simple switch,
  removal), and the oscillator warps (every mode, modulated, through unison / stereo phase
  / FM / Step tables / a polyphonic chord)) and checks the committed
  `core.golden.txt`; the C++ tests replay the same inputs and compare (PRNG bit-exact,
  tables ≤ 2e-6, engine samples — Synth voices included — ≤ 2e-6). Regenerate after an
  intended TS change:
  `npx vitest run -u tests/golden.test.ts`, then update the C++ port until ctest passes.
- **Native-only tests** — block-size independence (1…4096 frames give identical
  samples), table map vs `std::map` under random churn, pointer retirement, voice pool
  bounds, SPSC ordering under a concurrent producer, MIDI routing / CC map cases.
- **Host test** — the built VST3 through JUCE's VST3 host: instrument + MIDI, silent
  until played, note sounds / releases, note-on at its sample offset, block sizes 1–4096,
  sample rates 22.05–96 kHz, a parameter (mute) takes effect; with the host's transport
  playing the internal sequences stay silent and its MIDI plays the voice, until
  *Sequencer follows host* is turned on (and off again); state round-trip renders
  identical samples, garbage state ignored, editor opens (under xvfb in CI).
- **Web view, end to end** (`tests/WebTest.cpp`, Linux / WebKitGTK under xvfb): a fresh
  instance's page syncs its start state (one Synth voice in the full view, Generate,
  Timeline and Voice open) into the native document and saves its
  project; older projects take *Sequencer follows host* from their Host sync;
  Seed → Add batch clicked in the page reaches the engine; host automation of a voice
  parameter reaches the page's model and saved project; the saved state restores in a new
  instance (same timeline, voice parameters, no tables re-sent) and an add there is saved
  again; a MIDI note sounds; a voice switched to Synth in the page plays in stereo in the
  native engine, is saved, and plays after a restore before the editor opens; a voice on
  Preview batch plays Generate's unadded batch, which leaves the engine on undo and isn't
  saved; the in-page
  prompt / confirm answer correctly; Session → Export writes a `.mkwz` through the native
  save path and Session → Import reads it back through the native open path (the test
  bypasses the dialogs with `MKWAVEZ_TEST_SAVE_DIR` / `MKWAVEZ_TEST_OPEN_FILE`); the
  Session menu names the build and plugin mode; with a host MIDI note held and the transport
  stopped, the page's status has the voice live (osc B included), so it shows where it plays; Session → New (asking in-page first)
  replaces the session with the plugin's start session in the engine and the saved
  session, in the full view again.
- **Names and enums** (`tests/pluginParity.test.ts`, with the web tests on every push):
  every `SynthJson` name table (sources, destinations, LFO shapes, warps…), the C++ enums
  the engine indexes by, the CC map keys, the automatable host parameters and every Synth
  / LFO field, against `src/core` and `src/plugin/host.ts`. The golden renders use
  indices, so a name missing on the native side would pass them and do nothing.
- **Page side** (`tests/pluginHost.test.ts`, vitest with a fake JUCE backend, running
  main.ts's plugin boot): fresh / restored / unrestorable / silent native side, record
  wire format, autosave to native, transport echo suppression, automation, init values.
- Not yet run: pluginval and real DAWs.

## Plan

1. **P0: engine + plugin shell (done).** Audio core, formats, host transport, MIDI,
   parameters, state, minimal editor, CI.
2. **P1: the web app as the editor (done).** Engine port abstraction, session save /
   load (via the web app's session format), plugin boot (restore, reconcile, autosave), host transport /
   automation / MIDI settings sync, WebView editor with the embedded build. Every web
   feature (Seed / Mutate / Breed, formulas, Timeline, Wavetables, voices, sequences,
   undo, themes) works in the plugin because it is the same code.
3. **P2: hardening.** pluginval and DAW testing (Reaper, Bitwig, Live, Logic, FL),
   WebView quirks per host (focus / keyboard, resizing, HiDPI, Linux embedding), project
   Session export / import through native file dialogs, presets, a voice-count
   story beyond four automatable slots, more parameters (window / wavetable selection).
4. **P3: release.** Signing / notarisation, installers, licence choice (see Build).

A C++ port of generation (formula language, mutations, breed, write head) isn't needed
for the plugin; `plugin/core` stays the audio engine (and a base for hardware later).

## Known gaps

- Host parameters cover voices 1–4: the Simple voice fields (on a Synth voice: osc A's
  position, the amp settings, level, mute, octave) and 16 Synth parameters — Macro 1–4,
  cutoff, resonance, filter env, drive, osc A / B level, A / B warp, FM, pan, width, glide
  (`params::SynthField`; the page receives them as a nested `synth` patch). Everything else
  (tunings, windows, envelopes, LFOs, the matrix, modes) changes from the page or mapped
  MIDI CCs — or from host automation through a macro routed in the matrix. Restoring a
  project saved before the Synth parameters existed sets them from its document, so the
  saved sound isn't replaced by their defaults.

- Only voices 1–4 have host parameters (the page allows 8 voices; 5–8 play and save but
  can't be automated). Window, wavetable and interpolation aren't parameters.
- Mapped MIDI CCs patch the engine voice at once and the page's model a frame later; the
  host parameter for that field follows only via the page (editor open).
- With *Sequencer follows host* on, the sequencer follows the host's play state and tempo,
  not its bar position, and with the host playing Stop in the page can't stop it (the host
  transport wins). Tempo-synced LFOs lock their phase to the sequencer's clock only while it
  runs; otherwise they run free at the host's tempo (as in the browser while stopped).
- Without the editor open nothing generates (generation is UI-driven, as in the browser).
- Generate → Sample: audio files open through the native dialog (up to 256 MB) and are
  decoded by the platform web view's Web Audio, so the formats depend on it (WebKitGTK:
  the installed GStreamer plugins). Live input and tab capture need `getUserMedia` /
  `getDisplayMedia`, which embedded web views may not offer; the tab then doesn't offer
  them. Its audition player is a page `AudioContext`, which plays to the system output, not
  through the host. Resample (an offline render of a voice) works as in the browser.
- Undo history isn't saved (as in the browser). The plugin state holds every waveform's
  samples twice (the engine document and the session records); fine for typical sessions,
  ~75 MB at the 4096 cap. A session that can't be restored (e.g. saved by a newer
  version) is set aside in memory only while the editor is open.
- The theme and the Timeline thumbnail view are remembered through the web view's
  localStorage, which (depending on the platform's web view) may not persist between
  plugin sessions.
- Not yet tested: real DAWs, pluginval, the macOS / Windows web views (CI builds them;
  the end-to-end web view test runs on Linux only).
- The browser smoke test's "the strip follows the newest table" check fails in this
  environment on `main` as well (unrelated to the plugin).
